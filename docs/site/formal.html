formal

Lock the statement of a theorem a human approved, and see which proof files still have holes. For Lean 4 and Rocq. Every subcommand here runs offline.

A proof checker only checks that a proof matches its theorem. It cannot tell if the theorem is the one you wanted. The lock file pins the statement you approved, so a later change to it shows up in the audit instead of passing quietly.

The lock workflow

  1. A human reads a theorem statement and decides it says the right thing.
  2. Run paranoid formal lock <name>. It writes the statement hash to .paranoid-specs.json at the repo root.
  3. Commit the lock file.
  4. From then on, verify guards it. FV004 (critical) fires if a locked statement changes or its declaration disappears. FV007 (high) fires on any edit to the lock file. FV008 (medium) fires if the locked proof and the code it names change in the same diff.

An agent can run formal lock too. That is why FV007 exists: a change to the lock is always visible in the audit and deserves a human look. See the FV rules.

The spec lock file

.paranoid-specs.json sits at the repo root. FV004 compares the head against the lock as it was at base, so editing the lock in the same diff does not hide a change. 

{
  "version": 1,
  "specs": [
    {
      "name": "Parser.parse_total",
      "file": "Proofs/Parser.lean",
      "statement_sha256": "<64 lowercase hex characters>",
      "code": "internal/parser/parse.go",
      "note": "parse never fails on valid UTF-8"
    }
  ]
}

version must be 1. name, file, and statement_sha256 are required. code and note are optional; code turns on FV008 for that spec. The hash is the SHA-256 of the normalized statement (comments removed, runs of whitespace collapsed to one space), written as lowercase hex. Specs are kept sorted by name, then file. A lock file that does not parse at base is reported as a skipped check named formal-verification/spec-lock. The commands below treat a lock file that does not parse as an error.

paranoid formal lock

paranoid formal lock <name>... [--file path] [--code path] [--note text]

Run it inside the repository. It reads the tracked .lean and .v files in the working tree, finds each declaration by its exact qualified name (for example MyList.rev_rev), hashes its statement, and adds or updates its entry in .paranoid-specs.json. It creates the file if it is missing and keeps other entries. It prints one line per name: 

locked MyList.rev_rev (Proofs/Rev.lean) sha256:abcd12345678...
FlagMeaning
--file <path>Use only this proof file. Needed when a name is defined in more than one file.
--code <path>The code the theorem is about. Turns on FV008 for the entry.
--note <text>A short human note for the entry.

--code and --note apply to every name given. When you update an existing entry, its old code and note are kept unless you pass the flag again. If a name is defined in more than one file and you gave no --file, the command fails and lists the files. If a name is not found, it fails and suggests paranoid formal status. Nothing is written when any name fails.

paranoid formal unlock

paranoid formal unlock <name>...

Removes the entries with these names from the lock file. It fails with an error, and writes nothing, if a name is not locked.

paranoid formal status

paranoid formal status

Prints a plain text report in a fixed order. It has two sections.

  • Locked specs. Each spec is ok, drifted (the statement hash differs from the lock), or missing (the declaration or its file is gone).
  • Proof files. Each tracked .lean or .v file that has holes or axioms and escapes, with counts, for example Proofs/Rev.lean: 1 hole, 1 axiom or escape. none when all are clean.

A last line gives the totals. Only tracked files are read, and each is read once.

Exit codes

CommandExit code
lock, unlock0 on success, 3 on any error
status0 when no locked spec is drifted or missing, 2 when one is, 3 on any error

Exit 2 is the same "check failed" code that verify uses. Holes and escapes alone do not change the status exit code; verify reports those as FV001 and FV002. See Exit codes & CI.

Clean-room re-check (opt-in)

paranoid verify --formal-check

The rules above read text. --formal-check asks the proof checker instead. It rebuilds the proof project in a container, then asks the kernel which axioms each audited theorem really depends on. A sorry hidden behind a macro or a notation still shows up as sorryAx. Without the flag nothing changes in any report.

FlagDefaultMeaning
--formal-checkoffRun the re-check
--formal-imageper projectOverride the container image
--formal-timeout30mKill the re-check after this long. Real proof projects are slow

It uses the runtime chosen by --sandbox (docker or podman). With --sandbox none the re-check is listed as skipped, with no finding. See Sandbox & coverage for how the containers run.

Which project is rebuilt

Only a project at the repo root is found.

  • Lean: lean-toolchain plus lakefile.lean or lakefile.toml. Image debian:bookworm-slim. With the network on, the prep step installs the toolchain named in lean-toolchain and fetches the Lake dependencies. For Mathlib it also runs lake exe cache get. With the network off, the check step runs lake build, then #print axioms on a generated file.
  • Rocq: _CoqProject, or a dune-project with a Coq or Rocq stanza. Image rocq/rocq-prover:9.1. With the network off, the check step builds with dune build when there is a dune-project, otherwise from a makefile generated from _CoqProject. Then it runs Print Assumptions on a generated file. Both the rocq command and the older coq_makefile and coqc are handled.

Which theorems are audited

Every spec in the head lock file, plus every theorem declared in a changed proof file of the project's language, sorted by file and name, at most 200. Lean private declarations are left out, because they cannot be named from another file; any axiom they use also shows up in every public theorem that uses them. Rocq theorems in a Module are printed with their full path. A theorem the checker cannot find by name (for example a name made by a macro) is reported as FV012, never skipped quietly.

Allowed axioms

Lean allows propext, Classical.choice, and Quot.sound. Rocq allows none. A .paranoid.toml list adds to that set: 

[formal]
allowed_axioms = ["Classical.choice"]

sorryAx, Lean.ofReduceBool, and Lean.trustCompiler are never allowed. Listing one is a policy error (exit 3). See Team policy file. A Rocq theorem that ends in Admitted. shows up as an axiom named after the theorem, so FV010 fires on it.

The rules

RuleSeverityWhat it catches
FV009criticalThe proof project does not build in the clean room. The evidence is the first error lines
FV010highThe kernel reports an axiom outside the allowed set for an audited theorem. One finding per theorem and axiom
FV012highAn audited theorem got no answer from the kernel, for example an unknown name in the lock file. One finding per theorem, at its file and line
FV011infoThe re-check was asked for but could not run: no runtime, no proof project at the root, a failed toolchain install, or a timeout

When the re-check runs, the report lists the check formal-verification/recheck in checks_run. When it cannot run, the same name is in checks_skipped with the reason, and FV011 carries the reason as evidence.

What this does and does not prove

  • The rules read text. A determined agent can hide a hole behind a macro or a notation. The opt-in re-check asks the checker itself and closes that gap.
  • A proof is about a theorem. paranoid can show the theorem did not change since a human approved it. It cannot tell you the approved theorem says what you meant.
  • Proofs made for code in other languages are about a Lean model of that code. Tests that compare the model and the code can show they agree on many inputs, not on all inputs.

Online subcommands are coming

Subcommands that write proofs for you, such as fill and prove, are planned. They are not in this build. They will be the only parts of paranoid that call an LLM, and only when you run them with a key you set up. verify and the commands on this page never call a model or the network.
